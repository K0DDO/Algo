# 27. Хеширование: идея, хеш-функция, таблица, коллизия

## Зачем нужно хеширование

Во многих задачах нужно быстро сравнивать или находить объекты: строки, записи студентов, пароли, файлы, ключи в словаре.

Прямое сравнение строк или сложных объектов может быть долгим. Идея хеширования: сопоставить объекту короткое числовое значение - хеш.

Если два объекта имеют разные хеши, они точно разные. Если хеши равны, объекты могут быть равны, но возможна коллизия.

## Хеш-функция

Хеш-функция - это преобразование данных произвольного или большого объема в короткое значение фиксированного диапазона.

В лекции хеш сравнивается с:

- отпечатком пальца;
- структурой ДНК.

Это аналогия: хеш должен хорошо отличать объекты, но в обычных хеш-таблицах не обязан быть криптографически надежным.

## Свойства хорошей хеш-функции

Из лекций:

- уникальность;
- необратимость;
- изменяемость;
- быстрая вычислимость.

В контексте структур данных это можно уточнить:

- быстрая вычислимость: хеш считается быстрее, чем полное сравнение или сложный поиск;
- равномерность: ключи распределяются по таблице примерно равномерно;
- малая вероятность коллизий;
- детерминированность: один и тот же ключ дает один и тот же хеш;
- чувствительность к изменениям: похожие ключи не должны массово попадать в одни и те же ячейки.

Для криптографических хешей добавляются строгие свойства: необратимость, устойчивость к коллизиям и лавинный эффект.

## Хеш-таблица

Хеш-таблица - структура данных, реализующая ассоциативный массив:

```text
ключ -> значение
```

Операции:

- `insert(key, value)`;
- `find(key)`;
- `remove(key)`.

При хорошем распределении операции выполняются в среднем за:

```text
O(1)
```

Идея:

1. Считаем `h(key)`.
2. Приводим хеш к индексу таблицы.
3. Ищем или кладем элемент в соответствующее место.

## Сравнение структур

Из лекции:

```text
Структура                  Вставка     Удаление    Поиск
Массив                     O(n)        O(n)        O(n)
Список                     O(1)        O(1)        O(n)
Отсортированный массив      O(n)        O(n)        O(log n)
Бинарное дерево поиска      O(log n)    O(log n)    O(log n)
Хеш-таблица                O(1)        O(1)        O(1)
```

Это средние оценки для хеш-таблицы. В худшем случае при большом числе коллизий поиск может стать `O(n)`.

## Метод деления

Простейшая хеш-функция:

```text
h(key) = key mod m
```

где:

- `key` - целое числовое значение ключа;
- `m` - размер таблицы.

Часто `m` выбирают простым числом, чтобы уменьшить регулярные совпадения для структурированных данных.

Плюсы:

- очень быстро;
- просто считать вручную.

Минусы:

- плохой выбор `m` может приводить к множеству коллизий;
- если ключи имеют закономерность, распределение может быть неравномерным.

## Метод умножения

Формула из лекции:

```text
h(key) = floor(m * ((key * A) mod 1))
```

где:

- `0 < A < 1`;
- рекомендуемое значение связано с золотым сечением:

```text
A = (sqrt(5) - 1) / 2 ≈ 0.618
```

Пример из лекции:

```text
key = 123456
m = 10000
A ≈ 0.6180339887499
h(key) = floor(10000 * fractional_part(123456 * A))
       ≈ floor(41.151...)
       = 41
```

Метод умножения часто менее чувствителен к выбору `m`, чем метод деления.

## Аддитивный хеш строк

Простейшая идея для строки:

```text
hash = 0
while (*str):
    hash += code(*str)
```

Недостаток из лекции: такой хеш не различает анаграммы:

```text
h(XY) = h(YX)
```

Например, `ab` и `ba` дадут одинаковую сумму кодов.

Модификация: использовать побитовый xor, но он тоже слабый для многих задач.

## Метод середины квадрата

Идея:

1. Возвести ключ в квадрат.
2. Взять несколько средних бит или цифр результата.
3. Привести к диапазону таблицы.

Пример из лекции:

```text
int h(int key) {
    key *= key;
    key >>= 11;      // отбросить 11 младших бит
    return key % 1024; // вернуть 10 младших бит
}
```

Метод пытается использовать более "смешанную" среднюю часть квадрата.

## Полиномиальный хеш строк

Формула из лекции:

```text
hash(s) = (s0 + s1 * k + s2 * k^2 + ... + sn * k^n) mod p
```

где:

- `s_i` - код символа;
- `k` - число больше размера алфавита;
- `p` - модуль, часто простое число или взаимно простое с `k`.

Пример:

```text
k = 31
p = 1579
hash(abacaba) =
(61 + 62*31 + 61*31^2 + 63*31^3 + 61*31^4 + 62*31^5 + 61*31^6) mod 1579
= 62
```

Полиномиальный хеш особенно полезен для строковых алгоритмов: Рабин-Карп, сравнение подстрок, поиск повторов.

## Универсальное хеширование

Универсальное хеширование выбирает хеш-функцию случайно из семейства функций во время выполнения программы.

Формальное условие из лекции:

Пусть `H` - множество функций, отображающих ключи в `{0, 1, ..., m-1}`. Семейство называется универсальным, если для любой пары разных ключей `k1 != k2`:

```text
|{ h in H : h(k1) = h(k2) }| <= |H| / m
```

Грубо: для любой фиксированной пары ключей доля функций, на которых они сталкиваются, не больше `1/m`.

Это снижает риск плохих входов, потому что функция выбирается случайно.

## Коллизии

Коллизия:

```text
exists x != y: h(x) = h(y)
```

Коллизии неизбежны, если множество возможных ключей больше диапазона хешей.

Как бороться:

- выбрать более равномерную хеш-функцию;
- увеличить размер таблицы;
- использовать универсальное хеширование;
- использовать методы разрешения коллизий:
  - закрытая адресация, или метод цепочек;
  - открытая адресация;
  - двойное хеширование;
  - хеширование кукушкой.

## Где применяется хеширование

Из лекций:

- хранение паролей;
- защита медиафайлов от нелегального распространения;
- поиск вирусов;
- защита от фальсификации передаваемой информации;
- электронная подпись;
- блокчейн;
- ускорение поиска данных в базах данных.

Для структур данных обычно важны скорость и равномерность. Для безопасности важны криптографические свойства, и там нельзя использовать обычные простые хеши вроде `key mod m`.

## Ограничения

- Среднее `O(1)` зависит от хорошего распределения.
- Коллизии могут ухудшить операции до `O(n)`.
- Хеш-функция должна соответствовать типу данных.
- Для изменяемых ключей нельзя менять поля, влияющие на хеш, пока ключ лежит в таблице.
- Криптографический хеш и хеш для таблицы - разные инструменты.
